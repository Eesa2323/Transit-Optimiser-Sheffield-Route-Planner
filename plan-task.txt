Phase 1: Model the Core Domain & Graph (The DSA Foundation)Before touching ASP.NET, you need a clean object-oriented data structure to represent stations and connections.Define Your Entities:Station (Node): Has an Id, Name, and geographical coordinates (Latitude, Longitude).Edge (Connection): Represents a tram or bus link between two stations. It should have a DestinationStationId, TravelTimeMinutes, and LineName (e.g., "The Pink Line" or "Metrolink").Build the Graph Class (TransitGraph):Use an Adjacency List representation (a dictionary where the key is a StationId and the value is a list of outgoing Edge objects).Methods needed: AddStation(Station station), AddConnection(string fromId, string toId, int time), and GetNeighbors(string stationId).Phase 2: Implement the Routing Algorithm (Dijkstra’s Algorithm)This is the heart of your portfolio project. You'll write the shortest-path logic yourself.Leverage .NET’s Native Priority Queue:Modern C# (.NET 6+) has a built-in PriorityQueue<TElement, TPriority> class. This saves you from writing a custom heap from scratch while still proving you know how and when to use priority queues for graph traversal.Write Dijkstra’s Algorithm:Create a service class (e.g., RouteFinderService) that takes your TransitGraph, an OriginId, and a DestinationId.Keep track of shortest distances, previous nodes (to reconstruct the path), and visited states.Return a structured result containing the total travel time, list of stations visited, and transfer instructions.Phase 3: Create the Mock Data (Manchester Local Flavor)Instead of dealing with massive, messy raw GTFS files right away, start by hardcoding or JSON-loading a realistic subset of Manchester transit:Nodes: MMU All Saints $\rightarrow$ Oxford Road Station $\rightarrow$ St Peter’s Square $\rightarrow$ Piccadilly Gardens $\rightarrow$ Piccadilly Station.Give each edge realistic travel times (e.g., walking between MMU and Oxford Road = 4 mins; tram from St Peter's to Piccadilly Gardens = 2 mins).Load this data into your TransitGraph as a Singleton service when your application boots up, so it lives in memory for fast lookups $O(V \log V + E)$.Phase 4: Build the ASP.NET Core Web APIWrap your graph engine in a clean, professional Web API.Set up the Project:Run dotnet new webapi -n TransitOptimizer.Api (using .NET 8 or 9).Create a Controller or Minimal API Endpoints:Design an endpoint like GET /api/routes/plan?from=mmu-all-saints&to=piccadilly-station.Inject your TransitGraph and RouteFinderService via Dependency Injection.Handle Edge Cases:What if a user enters a station ID that doesn't exist? Return a clean 400 Bad Request or 404 Not Found with a descriptive error message.Phase 5: Testing & Portfolio Polish (Crucial for Hired Status)To stand out to recruiters, don't just finish the code—package it like a professional engineer.Write Unit Tests (xUnit or NUnit):Write tests for your Dijkstra implementation. Test edge cases:Traveling to the same station you are already at.Traveling to a disconnected station (no path exists).Verifying that it genuinely picks the shortest path when multiple routes exist.Interactive Documentation (Swagger/OpenAPI):ASP.NET includes Swagger out-of-the-box. Customize it with a good XML documentation summary so anyone opening your API can test the route planner interactively right in their browser.Bonus / Portfolio Flex (Frontend Map):If you want to go the extra mile, throw together a simple HTML file using Leaflet.js (a lightweight mapping library) that fetches from your ASP.NET backend and draws a visual line connecting the Manchester stations on an interactive map.
